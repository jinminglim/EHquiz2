W8Wireless Hacking: WLAN basics

Scope: WLAN components, Wi-Fi security standards, attack techniques & tools (rogue APs, wardriving, DoS/DDoS, key cracking), CIA attack tools, defences.

Components of a WLAN

ComponentWhat it does
Access Point (AP)Essentially a hub that lets wireless LANs connect to the network backbone. APs are what attackers look for.
Router / ModemModulates an analog signal to encode/decode digital info, and gives APs their connection to the Internet.
Wireless adapter (WNIC)Transmits/receives wireless signals and talks to other adapters in range. The Wi-Fi card in your laptop is a WNIC.
Wireless routerInterconnects devices inside one WLAN and can talk to other WLANs via an AP.

SSIDs, BSSIDs, probes and beacons

  • SSID (Service Set Identifier) names a WLAN, the same way a workgroup names a Windows network. It is configured on the AP as a unique, 1–32 character, case-sensitive alphanumeric name (32 bytes max).
  • The AP beacons (broadcasts) the SSID several times a second, so every WNIC in range sees it. One AP can beacon multiple SSIDs.
  • Default SSIDs (vendor defaults that companies never change) are an inherent weakness: they reveal the vendor and suggest default settings.
  • BSSID (Basic SSID) = the MAC address of the access point. netsh wlan show networks mode=bssid lists the Wi-Fi networks around you.
  • Probe request: sent by a station (client) when it needs information from another station, e.g. to find which APs are in range.
  • Beacon frame: sent periodically by the AP to announce itself, with timestamp, SSID and other parameters.
  • Uncontrolled RF medium: because APs beacon their info, walls are no longer barriers. Tools like Vistumbler show an attacker every AP, its SSID, MAC, channel and encryption.

A beacon is a shop with a neon sign flashing its name all day. A probe is a customer walking down the street shouting "Any shops open?". Either way, anyone on the street (the attacker) learns the shop names without going inside.

MAC addresses

  • A 48-bit unique identifier that every network device needs before traffic can be delivered to it.
  • The first 3 bytes are the OUI (Organizationally Unique Identifier), which identifies the vendor. The last 3 are the serial number. Slide examples: Cisco (Aironet) 00-04-96, Agere (Orinoco) 00-02-2D, Nokia 00-e0-03, Linksys 00-04-5a. So 00-04-5a-03-3c-0f is a Linksys device.

Rogue AP, Evil Twin and AP Honeypot

Rogue AP

  • An unmanaged (unauthorised) AP attached to the enterprise network, which makes it a big potential backdoor.
  • Very easy to set up: modern OSes share Internet, and software creates soft APs (e.g. Connectify).
  • Sometimes malicious, sometimes an unwitting, impatient employee.
  • It enables attacks on the wired network (ARP poisoning, DHCP, STP and DoS attacks), network mapping, scanning, and MITM / data sniffing.
  • Solutions: Network Access Control (not always effective, because of MAC spoofing) and periodic manual surveys.

Evil Twin

  • An attacker's AP configured the same as a legitimate one (same SSID and security settings) that overpowers the real signal. The attacker doesn't need to be close.
  • Most clients associate with the strongest signal, so the twin sees all their traffic (MITM). It can also use MAC spoofing to trick clients into sending passwords.
  • Why it works: IEEE 802.11b uses one-way authentication by default. The AP authenticates the user, but the user never authenticates the AP, so a user can't tell a fake AP from a real one.
  • The attacker needs the SSID, which is easy to get with a sniffer if it's broadcast or left at the default.
  • Wi-Fi hotspots are easy bait.

AP Honeypot

The attacker turns a laptop or USB Wi-Fi adapter into a soft AP (Virtual Router, Connectify, Virtual WiFi Router, My Public WiFi, My WiFi Router) that broadcasts the spoofed SSID of the legitimate AP, possibly with the legitimate AP's MAC too. Users connect, and the attacker harvests their information. Windows 7 "SoftAP" (hosted network):

netsh wlan set hostednetwork mode=allow ssid="ssid" key="passphrase" keyUsage=persistent

Rogue AP = an employee knocks a hole in the office wall and fits an unlocked side door, maybe just to get coffee faster. Evil twin = a crook opens a fake bank branch next door with the same logo and a bigger sign. Customers walk into whichever is closest and loudest, because they never check the bank's ID (one-way authentication).

Rogue AP is about an unauthorised AP plugged into your network (a backdoor inside). Evil twin is about impersonating a legitimate AP to lure clients (MITM outside). Both appear under "Rogue AP" in the attack table.

MAC spoofing and MAC filtering

  • Viewing your MAC: ipconfig /all.
  • Spoof via Device Manager: adapter → Advanced → Network Address. The first two hex characters must be 02, which sets the bit that marks the address as locally administered.
  • Spoof via Registry: HKLM\SYSTEM\CurrentControlSet\Control\Class\{4D36E972-E325-11CE-BFC1-08002BE10318}\0017\NetworkAddress
  • Spoof via tools: macchanger (Kali Linux), Technitium MAC Address Changer (Windows).
  • What spoofing lets an attacker do: (1) AP honeypot: give a rogue AP the legit MAC to divert traffic for MITM and replay attacks. (2) Bypass MAC address filtering, e.g. for free Wi-Fi.
  • MAC filtering allows or denies access by hardware address. The allow-list lives on the AP or on a RADIUS server. It's weak because MAC addresses are sent in the clear and can be sniffed, so authorised addresses are easy to find and copy.

MAC filtering is a bouncer checking name tags. Everyone's name tag is visible from across the room (sent in cleartext), and anyone can print a copy (spoofing).

W8Wi-Fi Security Standards

WEP RC4 · 24-bit IV · CRC-32→WPA RC4 + TKIP · 48-bit IV · Michael MIC (subset of 802.11i, interim fix)→WPA2 AES-CCMP · IEEE 802.11i · RSN→WPA3 SAE (latest & safest)

WEP: Wired Equivalent Privacy

  1. Based on the RC4 stream cipher.
  2. A secret key of 40 or 104 bits is combined with a 24-bit Initialisation Vector (IV).
  3. An Integrity Check Value (ICV), a CRC-32 checksum, is computed over the plaintext M.
  4. C = [ M ‖ ICV(M) ] ⊕ RC4( IV ‖ WEP key ). The IV is sent in the clear alongside the ciphertext, with a Key ID (KID).

WEP limitations (memorise all 6)

  1. Key management and size: usually 1–4 shared keys that are rarely changed.
  2. Dictionary attacks on the WEP key generator succeed quickly.
  3. The 24-bit IV is too short for cryptographic purposes.
  4. IV reuse produces identical keystreams. Adapters from the same vendor may even generate the same IVs.
  5. The IV is part of the RC4 key, and this weak seeding of RC4 is exploitable.
  6. The 32-bit ICV protects the payload but not the header, and CRC isn't cryptographic.

A 24-bit IV gives only ~16.7 million values. On a busy network that's like a raffle with 16 million tickets where tickets get re-sold: duplicates turn up quickly. Two packets encrypted with the same IV and key use the same keystream, so XORing them cancels the key out. That's like using a one-time pad twice.

WPA: Wi-Fi Protected Access (interim fix)

  • A subset of 802.11i with improved encryption and authentication (an IEEE 802.1X authentication server is optional).
  • Still RC4, but with 128-bit keys and a 48-bit IV (which can be split into a 24-bit IV and a 24-bit Extended IV).
  • TKIP (Temporal Key Integrity Protocol): keys are different per user and change dynamically, per frame. A key-mixing function takes the sequence number + base WPA key + transmitter MAC address and outputs a new key per packet. The IV doubles as the sequence counter.
  • MIC (Message Integrity Check): 64 bits, computed by the "Michael" algorithm and placed before the ICV. A frame counter defends against replay attacks.

Pre-Shared Key (PSK)Every user gets the same pass-phrase. Uses TKIP (less secure than AES). No authentication server.Personal mode: homes, small offices
IEEE 802.1XA server distributes different keys to each userEnterprise mode: business, government, education

WPA limitations

  • Weak PSK authentication: everyone shares one pass-phrase and there's no standard way to change the shared secret.
  • PSK is vulnerable to eavesdropping and dictionary attacks.
  • DoS: a flood of EAPOL messages requesting 802.1X authentication overwhelms the server.
  • TKIP was a stop-gap that still uses RC4, and it's vulnerable to the Beck-Tews keystream recovery attack. That attack only decrypts small portions of data (a single ARP frame takes about 14–17 minutes).

TKIP is like changing the padlock on every letter you post, but every padlock still comes from the same weak factory (RC4).

WPA2 (IEEE 802.11i)

  • Uses AES-CCMP (AES in Counter Mode with Cipher Block Chaining Message Authentication Code Protocol). AES replaces RC4.
  • Personal and Enterprise modes like WPA. Provides an RSN (Robust Security Network).

RSN via 802.1X / EAP: three players

Client (supplicant), Access Point (authenticator), Authentication Server (AS, e.g. RADIUS), talking EAP (Extensible Authentication Protocol).

  1. The AP sends a "request identity" message to the client.
  2. The client replies with its identity and preferred authentication method.
  3. The AP relays these to the AS.
  4. The client and AS exchange EAP messages to generate a common Master Key (MK).
  5. The AS sends "Server Accept", containing the MK, to the AP.
  6. The AP sends a final EAP Success to the client.

Key hierarchy

  • WPA2-Personal: a 256-bit PSK is generated from the plain-text pass-phrase. PSK + SSID + SSID length → PMK (Pairwise Master Key) → PTK (Pairwise Transient Key). The PTK is the session key between client and AP.
  • WPA2-Enterprise: needs an external RADIUS / AS. The MK comes from the client–AP–AS exchange, and the client and AP then derive the PTK. The AS gives each client a different MK.
  • PTK encrypts unicast traffic between client and AP.
  • GTK (Group Temporal Key) is created during the client–AP exchange in both modes and encrypts multicast/broadcast traffic.

The 4-way handshake (PTK/GTK distribution)

#DirectionContentsWhat happens
1AP → ClientEAPOL-Key(ANonce)Client now has both nonces and derives the PTK
2Client → APEAPOL-Key(SNonce, MIC)AP derives the PTK and generates the GTK
3AP → ClientEAPOL-Key(Install PTK, MIC, encrypted GTK)Client installs PTK + GTK

The 4-way handshake is two people who already share a secret (the PMK). Each shouts a random number (ANonce, SNonce), and both mix the secret with both random numbers to get the same fresh session key, without ever saying the secret aloud.

WPA2 limitations

  • Physical-layer attacks: RF jamming, data flooding, AP failure.
  • DoS attacks.
  • Layer-2 session hijacking.
  • Unprotected control and management frames (this is why deauth floods work).
  • AP spoofing (in Enterprise mode the attacker must be an authenticated client).
  • (Also offline dictionary cracking of a captured handshake when PSK is used, as in the CommView + Aircrack demo, and KRACK.)

WPA3 and SAE

  • Secure handshakes: older WPA connects device and router with a pre-shared key that brute force breaks relatively easily. WPA3 uses SAE: Simultaneous Authentication of Equals, which makes eavesdropping passwords much harder.
  • Stronger protection: the slide says "a user can make one offline password guess", i.e. each guess needs a live exchange. Brute-force attacks with hundreds of tries aren't possible against a captured exchange.
  • SAE sequence (slide 43): Beacon (RSNE) → SAE handshake (Auth-Commit ×2, derive PMK, Auth-Confirm ×2) → Association → the normal 4-way handshake (Msg1–4). SAE replaces how the PMK is derived. The 4-way handshake still follows.

With WPA2-PSK, an attacker can record the handshake and take it home, then try millions of passwords offline, like photographing a lock and picking it at leisure. With SAE, every guess means knocking on the real door and talking to the real AP. There's nothing to take home.

Explain why WEP is insecure and how WPA/WPA2 improved on it.
  • WEP: RC4 with a 40/104-bit static shared key plus a 24-bit IV. The short IV repeats, so identical keystreams get reused. The IV forms part of the RC4 seed (weak key scheduling). The CRC-32 ICV isn't cryptographic and doesn't cover the header. Keys are rarely changed, and dictionary attacks work.
  • WPA: TKIP gives per-user, per-packet keys (sequence number + base key + transmitter MAC), a 48-bit IV, a 128-bit key, a 64-bit Michael MIC and a frame counter against replay. But it's still RC4 (Beck-Tews), and the PSK is shared.
  • WPA2: AES-CCMP replaces RC4. 802.1X/EAP gives per-user master keys (Enterprise). The PMK→PTK/GTK hierarchy comes from the 4-way handshake.

Wardriving

  • The goal is to detect APs that aren't properly secured. Many have no password, so it pays off for attackers.
  • Wardriving itself isn't illegal. Exploiting the networks you find without permission is.
  • Kit: a laptop with a WNIC, an antenna, and software that scans for SSIDs. Warflying is the same thing done from a drone.

Wardriving is walking down a street noting which front doors are unlocked. Looking is legal. Walking in isn't.

DoS, DDoS and jamming

  • DoS: deny access to resources, usually by flooding the request queue with fake requests until legitimate users can't be served.
  • DDoS: many computers attack one target, usually a zombie network (botnet) of infected machines running the DoS tool. Tools: LOIC (Low Orbit Ion Cannon), HOIC (High Orbit Ion Cannon), XOIC, HULK, GoldenEye.
  • Jamming: a very powerful RF signal drowns out APs and clients. It can be deliberate or unintentional (other devices on the same frequency). It's similar to DoS, but rare because the equipment is expensive. You need a spectrum analyser to find the jamming source. Example software: My WIFIZone Internet Access Blocker.

Wireless sniffing

  • Sniffing can be fully passive: the attacker never transmits, and the card just listens on specific or all channels. This is the prelude to the other attacks.
  • A WNIC can run in RF monitor mode and promiscuous mode. Monitor mode captures packets without associating with any AP or ad-hoc network.

Monitor mode is sitting in a café hearing every table's conversation without joining any table.

WPA2 cracking demo (CommView + Aircrack-ng)

  1. CommView: capture data packets only, enable auto-saving logs, scan all channels (0.5 s each).
  2. Pick the WPA/WPA2 target and switch to single-channel mode on its channel.
  3. Wait to capture the handshake of a new device joining the network.
  4. Export the logs to Wireshark/tcpdump format (.cap).
  5. Aircrack-ng GUI: load the .cap, choose WPA, load a dictionary. The SSID and BSSID must be specified, and you must pick the network that has a handshake.

The WPA2-PSK crack is a dictionary attack on a captured 4-way handshake. It needs computing power and a password that's in the wordlist. KRACK is different: it is not a brute-force attack.

KRACK: Key Reinstallation Attack

  • Not brute force. It interferes with the 4-way handshake to reset the nonce.
  • Steps: the attacker (as MITM) blocks Msg4 from the client → the AP resends Msg3 → the client reinstalls the same key → the nonce (packet number) is reset, and on some devices it becomes 0.
  • Frame encryption is PTK + nonce → mix → per-packet key → keystream ⊕ plaintext. So nonce reuse means keystream reuse (in all WPA2 ciphers), which opens the door to replay and decryption.

Your bank's OTP token is meant to show a new code every time. KRACK is like tricking the token into rewinding its counter, so it repeats codes it's already shown and the attacker can replay or line them up.

Defences: Wi-Fi security measures

  • Change the default router authentication.
  • Use WPA/WPA2 rather than WEP.
  • Keep the router updated.
  • MAC filtering on the router (but it can be spoofed).
  • Change default AP settings, e.g. the default SSID, and disable SSID broadcast.
  • Stop radio waves leaving the building: Wi-Fi-proof paint and windows, Faraday cages.
  • Turn the router/AP off when not in use.
Describe the KRACK attack and why it breaks WPA2 confidentiality.

WPA2 encrypts each frame with a keystream derived from the PTK and a per-packet nonce. During the 4-way handshake the attacker, as MITM, blocks Msg4, so the AP retransmits Msg3. The client reinstalls the already-installed PTK and resets its nonce/packet counter (to 0 on some devices). Frames then reuse nonces, so the same keystream encrypts different plaintexts, which lets the attacker replay and decrypt traffic. It works without guessing the password, so it isn't brute force.

Explain how an evil twin works and how to defend against it.

The attacker clones the SSID and security settings of a real AP (sniffed from beacons or probes, or a default SSID), optionally spoofs its MAC, and transmits with more power. Clients pick the strongest signal, and 802.11 only authenticates the client, not the AP, so they connect to the twin. The attacker is now MITM and can sniff credentials. Defences: mutual authentication (WPA2/3-Enterprise with server certificates), WIPS / periodic surveys for rogue APs, user awareness on public hotspots, VPN, and limiting signal leakage.

Client-server web architecture

Web client (browser)→ HTTP request (cleartext or SSL) →Firewall→Web server (Apache, IIS, Netscape)→Web apps (plugins, Perl, C/C++, JSP)→ DB connection (ADO, ODBC) →Database
  • Traditional hacking went after OS network services (WU-FTPD, Sun RPC, NT IPC$). Firewalls block these, and internal back-end servers sit on non-routable private IPs.
  • Contemporary hacking goes in through the door that has to stay open. IANA assigned TCP 80 to HTTP and TCP 443 to HTTPS. HTTP is seen as "friendly" traffic, so "why fight the firewall?" Attackers enter via port 80, port 443 or tunnelling.
  • The web application is typically less secure than the web server.
  • All you need: a web browser, an Internet connection … and a clear mind.

The firewall is a security guard who checks every side door but has to leave the shop's front entrance (port 80/443) open for customers. Web attackers simply walk in as customers and then cheat at the counter (the web app).

Anatomy of a URL

protocol://ID:password@server:port/path

  • Protocol: the procedure for exchanging pages (e.g. HTTP).
  • ID:password: credentials for a secure server. Not recommended, because they're sent in plaintext.
  • Server name: the domain name, or the IP address.
  • Port: tells the server what kind of resource is requested. Default is 80.
  • Path: where the resource is on the server.

Web application footprinting and enumeration

Manual footprinting

Goal: understand the app's functionality, workflow and user interactions in order to identify the attack surface.

  • Browse and explore every visible feature (login, file upload, search…).
  • Locate input fields: forms, search boxes, uploads.
  • Note every GET/POST parameter in URLs and forms.
  • Explore links: internal, external, anchor, mailto:.
  • Review URL patterns for hidden resources or flows. Inspect page sources. Use OSINT tools.

Types of web hacks (the slide's escalation diagram)

URL manipulation→URL interpretation→Input validation (poor checking of user input)→SQL injection (extend SQL statements)

URL manipulation

  • Add ' or ; to a parameter (products.php?id=7') and watch for errors that reveal web server misconfiguration or SQL errors. This is part of the wider SQLi spectrum.
  • Tamper with parameters: ?id=-1. Modify status: ?id=7&status=del.

URL interpretation

  • DETURL.com: bypass download restrictions without an extra downloader.
  • Hidden paths: robots.txt. It tells search engine robots which parts of a site NOT to index, and it sits at the root (http://<root>/robots.txt). Attackers read it to find hidden directories.

robots.txt is a "STAFF ONLY: do not enter" sign. Polite visitors (search engines) obey it. Burglars read it as a map of the interesting rooms.

Input validation: directory (path) traversal

  • ../ (UNIX) or ..\ (Windows) means go up one directory. From C:\xx\yy\zz, ..\..\abc.txt reaches C:\xx\abc.txt.
  • It exploits inadequate security to access files outside the web root folder.
  • Root cause: insufficient filtering/validation of browser input.
  • Example targets: /etc/passwd, /etc/shadow%00, /etc/master.passwd, ../../etc/passwd%00, ../apache/logs/access.log.

Bypassing path traversal filters

  • Extension checks (the site requires .jpg or appends one): use a URL-encoded NULL byte, ../../../../etc/passwd%00.jpg. The check sees ".jpg", but the file-open call stops at the null, so everything after it is dropped. This works when the check is an API call that doesn't resolve URL encoding. A URL-encoded newline works too: %0a.jpg.
  • Disallowed characters: try forward and back slashes, and these encodings:

Encoding tricks are like a nightclub that bans the word "beer", so you order "b-e-e-r", "BEER" or "cerveza". A filter that checks only one spelling gets fooled, and the bartender (the server) decodes it and serves the beer anyway.

Core security problems (why web apps stay vulnerable)

  • Ignoring where sensitive information is stored and how it's at risk.
  • Under-using existing tools (application-aware firewalls, web vulnerability scanners).
  • Remediating without understanding what the tools report.
  • Assuming it's someone else's problem (e.g. pushing responsibility onto the cloud).
  • Misunderstanding the larger business goals and what management needs to hear.

W9SQL Injection (SQLi)

Definition: a code injection technique that exploits a vulnerability in the backend SQL database or web app. User input isn't filtered for string-literal characters embedded in SQL statements, or the app puts user-supplied data into a query without proper input validation and encoding. The attacker submits crafted input and tricks the SQL interpreter into running unintended commands.

SQLi is a Mad-Libs form letter: "Pay ____ the sum of $10." You write in "Bob. Also pay Eve $1,000,000". A careless clerk (the app) treats your data as part of the instructions. The fix is to keep data and instructions apart (parameterised queries / input validation).

SQLi attack procedure (6 steps)

  1. The app sends a form to the user.
  2. The attacker submits the form with SQL exploit data (e.g. ' or 1=1--).
  3. The application builds a query string that includes the exploit data. This is where the vulnerability sits.
  4. The application sends the SQL query to the DB (straight through the firewall).
  5. The DB runs the query, exploit included, and returns data to the application.
  6. The application returns the data to the user.

Login bypass demos

Demo 1: password injection (techpanda)

  • Typing a single ' into the password gives a system error, which shows the field is SQLi-vulnerable (the unbalanced quote breaks the query). Typing '' balances it again.
  • Payload: xxx') OR 1=1 -- ]. It completes the single quote and closes the round bracket, then appends an always-true condition to the md5(password) part. The rest is commented out.

Demo 2: username injection (testfire / Altoro Mutual)

  • Brackets: <username>') or 1=1 -- or <password>' OR 1=1 )# (# is the comment delimiter).

SQLi variations

  • Numeric fields don't need a quote: ?id=7 or 1=1.
  • If the comment character is blocked, craft the injection so it still balances the rest of the query: use ' or 'a'='a instead of ' or 1=1 --. The app's own closing quote finishes your 'a.
  • If the input sits inside ( ), use ' or 1=1)#.

' or 1=1 -- works because OR with an always-true condition makes the WHERE clause true for every row, and the comment removes the password check. If the exam asks "what does the -- do?", the answer is "comments out the rest of the query", not "subtracts".

Finding vulnerable sites: Google dorks

UNION-based extraction (testphp.vulnweb.com, MySQL)

  1. Detect: listproducts.php?cat=1' → SQL error.
  2. Count columns with ORDER BY n (sorts by column n, ascending by default), incrementing n until it errors. order by 12 errors, so there are 11 columns. A typical error is Unknown column '4' in 'order clause', which would mean 3 columns.
  3. Find the reflected ("vulnerable") columns: cat=-1 union select 1,2,3,…,11. UNION SELECT combines the results of two SELECTs (without duplicates) and needs the same number of columns. The -1 makes the original query return no rows, so only your injected row appears and the numbers on the page show which columns are displayed (e.g. 2, 7, 11).
  4. Fingerprint: replace a reflected column with @@version → 5.1.73 on Ubuntu, so probably MySQL.
  5. Tables: group_concat(table_name) from information_schema.tables where table_schema=database() → artists, carts, …, users. information_schema holds all the table-structure metadata.
  6. Columns: group_concat(column_name) from information_schema.columns where table_name='users'.
  7. Dump: concat(uname,0x3a,pass,0x3a,email,0x3a,name) from users --. 0x3a is the colon : used as a separator. You can repeat this in the other reflected columns (2 and 7).

ORDER BY probing is asking a waiter to "sort the menu by column 1, 2, 3…" until they say "there's no column 12". Now you know the menu has 11 columns. UNION with -1 is asking for "dish number −1 (which doesn't exist), and staple my own page to the menu". Only your stapled page comes back.

W9Web Hacking 2: XSS, CSRF, sqlmap, Defacement

What is XSS (Cross-Site Scripting)?

The attacker doesn't target the victim directly:

  1. The attacker injects malicious code into a vulnerable web server.
  2. The victim visits the vulnerable server (with their session cookie, e.g. s=01a4b8).
  3. The server serves the malicious code to the victim (<script>…</script>).
  4. The code executes on the victim's computer with the web server's privileges, e.g. GET /log?s=01a4b8 sends the victim's cookie to the attacker.

What arbitrary JavaScript in someone else's browser enables

  • Cookie theft: read document.cookie and send it to the attacker's server, e.g. to hijack the session ID.
  • Keylogging: register a keyboard listener with addEventListener and send keystrokes (passwords, card numbers) to the attacker.
  • Phishing: insert a fake login form through DOM manipulation, with its action pointing at the attacker's server.
  • Demo 1 (samsclass vulnphp): enter a normal name first to check that input is reflected, then scripts that cause a pop-up alert, redirection, or an embedded webpage.

CSRF / XSRF: Cross-Site Request Forgery

  1. The victim is logged into the vulnerable web site (has a session cookie).
  2. The victim visits a malicious page on the attacker's site.
  3. Malicious content is delivered, e.g. <img src=http://vuln/delete>.
  4. The victim's browser involuntarily sends the request (GET /delete) to the vulnerable site, with the victim's cookie attached automatically.
  • It's very hard for the target site to tell legitimate GET/POST requests from forged ones, because the forged ones come from a "trusted" browser with valid cookies.
  • testphp demo: the profile form userinfo.php has fields urname, ucc, uemail, uphone, uaddress.   • WebGoat demo: save the page locally and change the form's relative action to an absolute URL (http://localhost:8080/WebGoat/csrf/basic-get-flag) so the local copy submits to the real app.
  • Lecture summary: the victim must already be logged in to the legitimate site, is tricked into interacting with a malicious site, and unknowingly executes an action on the legitimate site.

CSRF is a forger slipping a cheque into a pile of papers you're signing. The bank sees your real signature (your session cookie) and pays out. The bank trusts you, and the attacker borrows that trust.

XSS vs CSRF. XSS runs the attacker's script inside the trusted site (it exploits the user's trust in the site). CSRF sends a forged request using the victim's logged-in session (it exploits the site's trust in the user's browser). CSRF needs the victim to be logged in. XSS needs the site to output unsanitised input.

W10Buffer Overflow & Format String Attacks

Overview: memory management → buffer overflow → format string vulnerability.

Memory management in C/C++

  • The program is responsible for its own memory management, which is very error-prone (think segmentation faults).
  • Typical bugs: writing past the bound of an array, and pointer trouble: missing initialisation, bad pointer arithmetic, use after free, double free, memory leaks.

What is a buffer overflow?

char buffer[4];     // valid indices 0..3
buffer[4] = 'a';    // BUFFER OVERFLOW: C lets you write past the end
  • C does no bounds checking. If the data written is user input an attacker controls, the bug can be exploited.
  • Normally the program just crashes, but an attacker can make it much worse:
    • Steal private information (e.g. Heartbleed)
    • Corrupt valuable information
    • Run code of the attacker's choice
  • Why it matters: C/C++ is still everywhere, in Windows, Excel, Linux, Mozilla, MySQL, and in critical systems: OS kernels and utilities, high-performance servers (Apache, nginx), embedded systems.

Memory layout (Linux process model, 32-bit)

0xffffffff (4G): Cmdline & env (set when the process starts)
Stack ↓ grows down: int foo(){ int x; } (runtime)
… free space …
Heap ↑ grows up: malloc(sizeof(int)) (runtime)
Uninitialised data (BSS): static int x;
Initialised data: static const int y = 10;
Text (machine instructions, e.g. push %ebp)
0x00000000
  • The process thinks it owns all 4 GB. In reality these are virtual addresses, and the OS/CPU maps them to physical addresses.
  • The data and text segments are known at compile time. Stack and heap are runtime.
  • The stack and heap grow in opposite directions. The compiler emits instructions that adjust the stack size at runtime (push 1, push 2, push 3 moves the stack pointer toward lower addresses). The heap is provisioned by the OS and managed in-process by malloc.

Function calls and the stack frame

Calling a function stores: the function arguments, the return address and the base pointer, all on the stack. Returning restores the stack state, also from the stack.

void foo(char *arg1, int arg2, int arg3) {
    char loc1[4];
    int  loc2;
}
lower addresses                                                     0xffffffff
 … | loc2 | loc1 | saved %ebp | saved %eip (ret addr) | arg1 | arg2 | arg3 | caller's data
            ▲ locals            ▲ %ebp points here       ▲ args pushed in REVERSE order
  • Arguments are pushed in reverse order (arg3 first). Locals are pushed in the order they appear (the compiler may optimise, or keep them only in registers).
  • The absolute address of loc2 isn't known at compile time, but its relative address is: always 8 bytes before the frame (base) pointer %ebp.
  • %esp = stack pointer (top of stack). %ebp = base/frame pointer (fixed reference for the current frame). %eip = instruction pointer (next instruction).

x86 calling convention

WhoSteps
Caller1. Push the arguments in reverse · 2. Push the return address (the next %eip) · 3. Jump to the function's address
Callee (prologue)1. Push the old frame pointer (push %ebp, which backs up the caller's base pointer) · 2. Set %ebp = current %esp · 3. Push the local variables
Returning (epilogue)1. Reset the previous frame: %esp = %ebp, %ebp = (%ebp) · 2. Jump back to the return address: %eip = 4(%esp), i.e. the saved return address that sits just above the saved %ebp (4(%ebp))

The stack is a pile of cafeteria trays. Each function call puts a tray on top holding its ingredients (locals), a sticky note saying "where I came from" (saved %ebp), and a bookmark saying "where to continue reading when done" (the return address). Finish the function, take the tray off, go back to the bookmark.

Stack overflow (stack smashing)

void f(int x) {
    char buf[8];
    gets(buf);          // gets() has NO length limit
}
void main() { f(…); … }
void format_hard_disk() { … }

stack:  [ buf[0..3] ][ buf[4..7] ][ saved ebp ][ Return addr ][ x ][ main() ]
                       overflow writes upward  ───────────►  overwrite ret addr
  • If gets() reads more than 8 bytes, the extra bytes spill upward over the saved frame pointer and then the return address.
  • When f returns, the CPU jumps to the attacker-chosen address, e.g. format_hard_disk() (or injected shellcode). That's control-flow hijacking.

Each locker in a row holds 8 items. You stuff in 20, and the extras spill into the next lockers, including the one holding the note "after class, go to Room 101" (the return address). Rewrite the note and the program walks wherever you want.

The lab may expect these even though they're not on the slides:

  • Little-endian (x86): the address 0x080491b6 is written as the bytes \xb6\x91\x04\x08. Payload = padding to reach the return address + new address.
  • Offset = buffer size + saved EBP (4 bytes on 32-bit) + any alignment. Find it with a cyclic pattern in gdb, e.g. pattern create/pattern offset, or by checking EIP after a crash.
  • Unsafe functions: gets, strcpy, strcat, sprintf, scanf("%s"). Safer ones: fgets, strncpy/strlcpy, snprintf.
  • Mitigations: stack canaries (a random value before the return address, checked on return), ASLR (randomises addresses), NX/DEP (stack not executable). Labs often disable these, e.g. -fno-stack-protector -z execstack -no-pie.
  • NOP sled (\x90…): lands execution safely into shellcode when you only know the address roughly.

Format string attacks

  • Another way to corrupt the stack. C format strings contain special characters like %s: printf("Cannot find file %s", filename);
  • printf("Cannot find file %s"); has no argument, so printf still goes looking for one and uses whatever is on the stack.
  • The real bug: printf(string) where string is user-supplied.

How it looks on the stack

printf("%d %d %d", a, b, c);   stack: [ "%d %d %d" ][ a ][ b ][ c ]   → prints a, b, c
printf("%d %d %d");            stack: [ "%d %d %d" ][0xb45692][0x23e567][0x11111]
                                → printf just takes whatever values are on the stack and prints them as a, b, c
SpecifierEffect in an attack
%xReads and prints (hex) bytes from the stack. %x %x %x … dumps the stack and leaks sensitive data
%dSame idea, printed as decimal
%sTreats the next stack value as a pointer and prints the string at that address, giving an arbitrary read (or a crash if the address is invalid)
%nWrites the number of characters printed so far to the address on the stack, which lets the attacker corrupt memory (write). This is what makes format string bugs so potent.

Advanced format string attack

"\xEF\xCD\xCD\xAB %x %x ... %x %s"   → with the right number of %x, prints the string at address 0xABCDCDEF
"\xEF\xCD\xCD\xAB %x %x ... %x %n"   → writes (chars printed so far) INTO address 0xABCDCDEF

The attacker puts the target address at the start of their own format string (which is itself on the stack). The %xs "walk" printf's argument pointer up the stack until the next specifier lines up with those address bytes. Then %s reads from it, or %n writes to it. The bytes are reversed (EF CD CD AB) because x86 is little-endian.

The easy fix

printf(str);          // VULNERABLE: the user controls the format
printf("%s", str);    // SAFE: the user input is only ever data

printf is a robot secretary filling in a form letter: "Dear %s, you owe %d". It blindly grabs the next item from the in-tray (the stack) for every blank. If the attacker writes the template, they can add 50 blanks and the robot reads out 50 confidential papers (%x). %n is a blank that says "write down how many letters you've typed so far, at this address", so the robot becomes a pen the attacker controls.

  • %n writes. %x, %s and %d read.
  • The fix is printf("%s", str), not "use %n carefully" and not "increase the buffer size".
  • Buffer overflow = too much data written into a buffer. Format string = user data interpreted as a format. Both corrupt the stack.
Explain how a stack-based buffer overflow lets an attacker execute arbitrary code.

Local buffers live on the stack below the saved %ebp and the saved return address. C doesn't check bounds, so an unbounded copy such as gets(buf) with more input than buf holds overwrites the adjacent memory, including the return address. When the function returns, the CPU pops the attacker-supplied value into %eip and jumps there: to an existing function (e.g. format_hard_disk), or to shellcode the attacker placed in the buffer. Mitigations: bounded functions (fgets), stack canaries, ASLR, NX/DEP, and safer languages.

What is a format string vulnerability? How is it exploited and fixed?

It happens when user input is passed as the format argument, e.g. printf(input). printf reads one stack value for each specifier, whether or not real arguments exist. %x leaks stack contents. %s dereferences a stack value and reads arbitrary memory. %n writes the count of printed characters to an address, so with a crafted address at the start of the string plus padding %xs, the attacker can write to an arbitrary location (e.g. overwrite a return address). The fix is printf("%s", input).

Scope: backdoors · trojans · rootkits · keyloggers.

  • A backdoor is an access point created to bypass normal target defences. Sometimes it comes from a vulnerability. Other times the attacker installs an entry point on a compromised target to finish the attack later.
  • Most often found in Advanced Persistent Threats. To be effective it must be hidden or disguised.

Sniffing backdoors (stealthy, with no open listening port)

  • Attackers don't want to get caught, so a backdoor doesn't have to sit listening on a port. A sniffer gathers traffic instead.
  • Non-promiscuous sniffing backdoor: sniffs traffic for one target (its own host). Example: cd00r. It only opens a listener after receiving a sequence of TCP SYN packets to a defined list of ports in the correct order, e.g. SYN to X, Y, Z, then a temporary root shell listener on port 5002.
  • Promiscuous sniffing backdoor: sniffs all LAN traffic. Example: the backdoor sits on the DNS server but sniffs packets addressed to the WWW server, where there's no backdoor at all. In a switched network the attacker may use ARP cache poisoning. This is very confusing for investigators.

A normal backdoor is a spare key under the doormat, which anyone searching the porch could find (an open port). cd00r is a door with no keyhole that only appears after a secret knock (SYN to ports X, Y, Z in order). A promiscuous backdoor is a spy in the house next door, reading your post through the window. Investigators search your house and find nothing.

Trojans

  • A Trojan horse is any malicious program that gets into a computer by misleading users about its true intent. The name comes from the Greek wooden horse at Troy.
  • Typically aims to: take control of the victim computer, steal data, and insert more malware.

ProRat (RAT = Remote Access/Administration Trojan)

  • The lecture's example of a RAT: it gives unauthorised remote access and control, installs stealthily, runs in the background, accesses keystrokes and files, and can run arbitrary commands.
  • Facts the lecture highlights: the attacker builds a "server" component that the victim is tricked into running, and it can disable antivirus/firewall. The attacker then connects to it (lecture demo: port 5110).

Tricking users: wrappers

EXE wrappers embed the backdoor in an innocent-looking program by packing files into one archive executable that extracts and runs them, visibly or hidden. Wrappers may cause antivirus false positives.

Weevely: a PHP web backdoor

Generates a small, password-protected PHP agent. Once the agent sits in a web server's document root (the lab used XAMPP's htdocs), the attacker connects to it over HTTP and gets a remote shell on the web server. It's a "web shell" kind of backdoor.

A poisoned tongue (the kernel) means you can't trust your own sense of taste, so everything looks fine even when it isn't.

  • Rootkit: a type of Trojan that keeps itself hidden and gives the attacker root/administrator access. It intercepts common API calls (e.g. FindFirstFile/FindNextFile) so antivirus scans never see it, modifies dir, ls and ps so they don't show its files and processes, and cleans up log messages left by the exploit.
  • Traditional rootkits are more powerful than application-level backdoors (BO2K, Netcat), because those run as separate programs that are less easily hidden.
  • Kernel-level rootkits can hide processes, files, folders and network use (sniffers, port listeners), and can redirect execution. There are three ways to implement one: (1) a Loadable Kernel Module (kernel-mode drivers on Windows), (2) patching the kernel image on the hard drive, (3) altering the kernel in memory on a running system.

Example: the Sony XCP rootkit

  • Mark Russinovich was testing a Windows rootkit scanner he was developing and found a rootkit already on his own machine.
  • The source was Sony audio CDs with XCP "copy protection". The CD's autorun.exe runs automatically and installs the rootkit.
  • Primary purpose: modify the Windows CD driver so any process reading an XCP CD gets garbled output. Secondary purpose: make itself hard to find and uninstall. After complaints, Sony released an uninstaller.

Defences against application-level Trojans

  • Antivirus tools: detect attack-tool fingerprints (file names, registry key settings, services). Update definitions weekly.
  • Know your software: only run software from trusted developers. Check digital signatures and a digital fingerprint/hash (e.g. MD5) to spot trojanised programs.
  • Don't use single-purpose checkers (e.g. a "BO2K remover"). The checker itself may be a Trojan that installs BO2K and tells you the machine is clean.

Keyloggers

  • Almost all information flows from the user to the computer through the keyboard. A keylogger records all email/IM sent, websites visited and passwords typed.
  • Some are installed by malware, e.g. KeyBase (since Feb 2015), which captures banking passwords and sends them to the remote attacker. The data can be read locally or sent over the Internet.

Tools: Key Logger Pro (Shift+Ctrl+Alt+K to show it. The free edition doesn't log websites visited or the clipboard). Actual Keylogger (Shift+Ctrl+Alt+F7 to show it. Captures keyboard and Internet activity, sends logs by email, LAN or FTP, and takes screenshots at intervals).

A hardware keylogger is a wiretap on the keyboard cable. No antivirus can see it because it isn't software, but someone had to walk up to your desk to fit it.

Compare application-level Trojans, traditional rootkits and kernel-level rootkits.

An application-level Trojan is a separate malicious program (Sub7, BO2K, Netcat) running next to good programs. It's the easiest to detect (process lists, AV signatures). A traditional rootkit replaces critical OS binaries (login, ps, ifconfig) with trojaned versions that hide the attacker and provide a backdoor (Lrk6, T0rnkit). File-integrity tools such as tripwire can detect it. A kernel-level rootkit patches the kernel (LKM, on-disk kernel image, or in-memory), so user binaries stay untouched but every system call can be filtered, hiding files, processes and network use (Knark, Adore). It's the hardest to detect because the OS itself lies.

What is a sniffing backdoor, and why is it stealthier than a listening backdoor?

Instead of opening a listening port (visible to netstat or a port scan), it passively sniffs traffic and waits for a trigger. Non-promiscuous (e.g. cd00r) watches only its own host's traffic and opens a temporary shell port only after a secret sequence of SYN packets to specific ports in order (port knocking). Promiscuous sniffs the whole LAN, so it can sit on one machine (the DNS server) and react to packets sent to another (the WWW server), which misdirects investigators.

Steganography in image files

  • An image file = header (precise, little spare capacity) + pixels (most of the file).
  • Each pixel has 3 colour components, R, G, B, each 8 bits (256 values). A full-colour image has 3 colour planes.
  • Looking at one plane bit by bit: bit 7 (MSB) holds most of the visual information, and bit 0 (LSB) looks like random noise.
  • LSB replacement: swapping the LSB for payload bits is unlikely to be noticed, which gives a payload capacity of 1/8 = 12.5%. Using bits 0 and 1 gives 2/8 = 25%.
  • Choose the cover carefully: the baboon image is a good cover because its colours change quickly everywhere. Scenery with large flat areas (sky, sea, mountains) changes little, so altered LSBs become noticeable.
  • Steganalysis: public tools exist. One technique is comparing pixel-intensity histograms of the cover and stego image (the slide shows baboon histograms before and after hiding data).

LSB stego is like changing prices from $9.99 to $9.98. Nobody notices the last cent, but the pattern of cents can spell a secret message. On a plain blue sky, though, every "pixel price" is the same $5.00, so a sudden $5.01 stands out.

1 bit of 8 = 12.5%, 2 bits of 8 = 25%. LSB = bit 0 = noise = safe to hide in. MSB = bit 7 = the picture itself.

Making files "undeletable"

  • Change permissions, then rename and hide the file.
  • Prevent (thewindowsclub tool): set a hotkey (e.g. Ctrl-P) to toggle it. It disables right-click functions: cut, copy, paste, delete, rename.
  • Inconspicuous filenames: a trailing space, period or underscore, e.g. abcde .txt, abcde..txt, abcde_.txt. In dir output they look normal, so the obvious del abcde.txt fails.

  • Clearing: filter by event level, then Action → Clear Log…. This wipes the whole log. Event log files can't be opened or edited with a standard file editor.

Logs are CCTV footage. Clear Log erases the whole tape, and a blank tape is itself suspicious. Winzapper cuts out only the frames you appear in. That's stealthier, but you need the keys to the control room (admin).

Explain how LSB steganography works and its capacity and limitations.

Each pixel's R, G and B components are 8 bits. The least significant bit holds almost no visual information (it looks like noise), so replacing it with payload bits doesn't visibly change the image. Capacity is 1 bit in 8 = 12.5% of pixel data (25% if bits 0–1 are used). Busy, high-detail covers (the baboon) hide changes well. Smooth areas (sky, sea) reveal them. Steganalysis, such as histogram comparison, can detect the statistical changes.

W11Advanced Persistent Threats (APT)

APTs are tools and techniques used to launch an attack that cannot be stopped by conventional security mechanisms. Scope: attack cycle · characteristics · real-world examples · current scenarios.

A typical APT attack cycle

Preparation: Define target → Create/acquire malware → Research the target → QA for detection→ Infection: Infect the target→ Deployment: "Call home" → Expand access → Extract data→ Persistence: Enhance presence → Stay undetected↺
  • Phases are gradual and incremental (extended, repeated reconnaissance, scanning and enumeration).
  • Coordinated across attack points.
  • A continuous effort to stay stealthy (may cover tracks repeatedly).
  • Will try many times with different methods (persistent).
  • A C&C (Command & Control) server directs further attacks.
  • Cloud computing and BYOD increase the target's attack surface.

A phishing attack cycle

1. Targeted malicious email sent to user→2. User clicks a link to a malicious website→3. Website exploits a client-side vulnerability→4. Drive-by download of the malicious payload↺
  • The target user or group is chosen (e.g. through social engineering). If the first email is ignored or deleted, a different email is sent.
  • The downloaded payload is e.g. a backdoor. Stealth must be maintained so phase 1 can be repeated.

Spear-phishing demo: Social Engineering Toolkit (SET) on Kali

SET → Social-Engineering Attacks → Spear-Phishing Attack Vectors → Create a FileFormat payload, a Word document (RTF) that overflows a buffer so a listener/rootkit can be placed on the victim → choose the payload Metasploit Meterpreter → enter the listener IP and port → SET creates template.rtf (rename it if you like) → email it (Google may block it). Notice how this ties back to Week 10: a buffer overflow in the document reader is the infection vector.

The targeted attack model

  1. The attacker sends phishing emails with malicious attachments (DOC, PDF, XLS) → 2. the user interacts with the email → 3. the system is compromised → 4. remote management and administration tools are installed → 5. other machines are attacked and compromised → 6. sensitive information and critical data are located → 7. data is exfiltrated from remote machines. (This mirrors the RSA attack.)
  • Intelligence gathering: OSINT (collecting intelligence from public, openly available resources).
    • Passive mode: no interaction (no traffic) with the target at all.
    • Semi-passive mode: generic information-gathering that produces normal-looking traffic, e.g. DNS queries or WHOIS lookups.
  • Threat modelling: map the target environment and sort assets by importance and value into primary and secondary targets. Assess which domains are most likely to reveal the attack and which might invite retaliation.

Real-world examples

RSA breach (March 2011)

  • Information was stolen that affected some 40 million two-factor authentication tokens (SecurID devices, used in industry and government, showing a 6-digit number every 60 seconds).
  • Spear phishing with a backdoor: two different targeted phishing emails went to four workers at RSA's parent company EMC. The attachment was named in the subject line as "2011 Recruitment plan.xls". When one recipient opened it, it installed the Poison Ivy backdoor (RAT).

APT characteristics

Targeted, low-profile · extremely stealthy · highly motivated and determined · well-financed · coordinated across attack points · very low to zero target downtime (they don't break things). Many organisations run for years without knowing they've been breached.

A normal hacker is a smash-and-grab thief: noisy and gone in five minutes. An APT is a professional heist crew. They study the bank for months, get a job inside, copy the keys, take a little at a time, and leave a member on staff so they can come back. Nobody notices for years.

Quasar RAT (lecture demo, concepts only)

  • An open-source RAT used to show remote management and administration in the targeted attack model. The attacker's machine plays the C&C server.
  • Concepts worth remembering: a client is built with the C&C address and port. A mutex setting ensures only one instance runs on a system. Other settings cover installation, appearance (assembly info) and monitoring (keylogging). The client reaches victims through phishing or USB drops.

Shadow Force: DLL hijacking (Trend Micro, 2015, a South Korean company)

  • Windows has a DLL search order, similar to $PATH for executables. The attacker only needs to work out where to put a hostile DLL earlier in the search path, and give it the name of a legitimate DLL. Windows finds the hostile one first and loads it.
  • The real attack: Windows starts the MSDTC (Microsoft Distributed Transaction Coordinator) service, which coordinates transactions across databases, message queues and file systems. Its MTxOCI component searches the registry for three DLLs: oci.dll (from Oracle), SQLLib80.dll and xa80.dll.
  • The attacker renames a backdoor to oci.dll and places it in %SystemRoot%\system32\, then kills MSDTC (taskkill /im msdtc.exe /f). MSDTC reloads itself, finds the hostile oci.dll and opens Shadow Force.
  • Variants: DLL or EXE, 32- or 64-bit. The installer decides which to fetch (SuperBot.exe or SuperBotx64.exe). The EXE version connects to an IRC C&C server like a normal IRC bot. The DLL version installs npf.sys from the open-source Wireshark project, which has a valid signature, so Windows loads it and it can capture network packets.

DLL hijacking is a manager who calls out "Bob from Oracle, please come in" and takes the first Bob in the queue. The attacker plants a fake Bob (hostile oci.dll) at the front of the queue (system32), then forces the manager to restart his round (taskkill MSDTC) so he calls "Bob" again.

Defending against APTs

Primary considerationPenetration resistanceInformation-system resilience
Adversary locationOutside the defensive perimeterInside the defensive perimeter

  • Boundary protection is necessary but not sufficient for agile defence.
  • Agile defence measures: compartmentalisation and segregation of critical assets · targeted allocation of security controls · virtualisation and obfuscation · encryption of data at rest · reconstitution to a known secure state after failure.
  • Preventive solutions: Behavioural Analysis (cyber-attack detection → attack location ID → IP or AS blocking) · Security Monitoring (maximise QoS → risk analysis) · Incident Response (attack validation → blocking policies → inform subscriber).

Boundary protection is a castle wall: it keeps invaders out. Agile defence is a ship with watertight compartments: assume the hull is already breached and keep sailing anyway. APTs are already inside the walls, so you need both.

Describe the RSA (2011) attack in terms of the APT / targeted-attack model.

Recon identified a small set of EMC employees (intelligence gathering). Two different spear-phishing emails were sent to four employees with an Excel attachment, "2011 Recruitment plan.xls", carrying an exploit (infection). One employee opened it, and the Poison Ivy backdoor (a RAT) was installed and "called home" to C&C. The attackers then moved laterally, gathered data about SecurID and exfiltrated it, affecting about 40 million tokens. It shows the APT traits: targeted, stealthy, persistent (multiple emails) and well-resourced.

Explain DLL hijacking using the Shadow Force example.

Windows looks for DLLs in a defined search order. If an attacker can write a malicious DLL with a legitimate name to a location searched earlier (or where the expected DLL is missing), the service loads the attacker's code with its own privileges. In Shadow Force, MSDTC's MTxOCI component loads oci.dll (normally from Oracle). The attacker dropped a backdoor oci.dll into system32 and killed msdtc.exe, and on restart the service loaded the backdoor. That gave stealthy, persistent execution inside a trusted Windows service.
